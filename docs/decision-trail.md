# Decision trail

Why blitz looks the way it does, in the order the decisions were made.

| # | Decision | Why |
|---|---|---|
| 1 | Speed comes from never compiling the same thing twice, not from a faster compiler. | rustc does the work; cargo's own overhead is a fraction of a second. A faster linker or backend gives 2-5x at best. Only reuse of earlier work gives two orders of magnitude, which is how Bazel, Buck and sccache get their wins. |
| 2 | Headline benchmark: clean target, fresh checkout, warm cache, against `cargo build` on the same checkout. Cold-cache and edit-one-file numbers are reported next to it. | That is the case every new CI pull request and every branch switch hits. Reporting the cases blitz does not speed up keeps the number honest. |
| 3 | Two caches over one content-addressed store: whole-build (skip cargo entirely) and per-unit (blitz as `RUSTC_WRAPPER`). | The whole-build hit is what makes a build take milliseconds. The per-unit cache makes the miss path cheap after any change, because dependencies are restored instead of rebuilt. |
| 4 | Restore by `std::fs::copy` into a temp file and rename. | On APFS, btrfs and XFS the copy is a copy-on-write clone, so it costs about the same as a hard link without sharing mutable bytes with the cache. |
| 5 | Per-unit cache skips incremental, `bin`, `dylib` and `cdylib` units. | Incremental units are already cached by rustc itself. Linked outputs pull in system libraries and linkers that blitz cannot hash. sccache draws the same line. |
| 6 | (Superseded by 12.) Registry and git dependencies are keyed by their normalized source path, without a dep-info pre-pass. | Their sources cannot change for a given path (crates.io versions and git revisions are immutable, and `Cargo.lock` pins both), so the pre-pass would only cost time. |
| 7 | Read-only cache tiers (`BLITZ_CACHE_RO`). | CI pull requests read main's cache but write only to their own, so a pull request cannot plant artifacts in the cache main's builds use. |
| 8 | The target directory is not part of the whole-build key. | Artifacts are stored relative to it, so a restore into another checkout or `--target-dir` works. Proven by restoring into a second target dir and running the binary. |
| 9 | Proofing found three stale-hit holes, each fixed before merge: relative `rerun-if-changed` paths resolved against the wrong root, `..` paths compared textually, and path dependencies outside the workspace not hashed at all. | A stale hit is the worst bug blitz can have; each hole was reproduced with a purpose-built workspace, fixed, and re-run. |
| 10 | Symlinked or unwalkable directories make `blitz build` fall back to plain cargo. | Guessing which side of a symlink is an input risks a stale hit; plain cargo is always correct. |
| 11 | Lines are 120 columns (`rustfmt.toml`). | The modules were written at that width; one formatter setting keeps `cargo fmt --check` in CI meaningful. |
| 12 | A git checkout keys the source files a dep-info pre-pass reported, `# env-dep:` lines included; only an unpacked registry crate (`.cargo-ok` next to its `Cargo.toml`) skips hashing its sources. | A dependency that reads an environment variable produces different bytes when the value changes, and skipping the pre-pass for registry and git units turned that into a stale hit. Git checkouts can be patched in place, so they are not treated as immutable. Registry units no longer pay the pre-pass for it; see 20. |
| 13 | `staticlib` is no longer cached. `proc-macro` stays cacheable, with the linker binary (`-C linker=` or `cc`, by size and mtime) and `SDKROOT`, `DEVELOPER_DIR`, `MACOSX_DEPLOYMENT_TARGET` in the key. | A linked artifact depends on the linker and the SDK, not only on the sources. The residual risk is a shim linker that starts forwarding somewhere else while keeping its own size and mtime; that cannot be seen from here, and the SDK variables cover the common macOS case. |
| 14 | Blob contents are not verified on restore unless `BLITZ_VERIFY=1`. | A blob only ever appears by atomic rename, so a mismatch means a disk fault, and re-hashing a 100 MB binary on every hit costs more than the hit saves. With the switch set, a copy that does not match its digest is deleted from a writable tier and reported as an error, which the caller treats as a miss. |
| 15 | A restored output name must be one plain file name under `--out-dir` that starts with a prefix the unit writes; otherwise the entry is a miss. | Entries are JSON read off the disk, not a promise. A name such as `../../bin/sh` would otherwise be joined onto the output directory and written outside it. |
| 16 | A normalizer root matches only at a path boundary, and a build script `OUT_DIR` that contains a symlinked directory, a broken link or a special file makes the unit uncacheable. | `/w/target` must not rewrite `/w/target-old` into a path that never existed, and what a tree of links resolves to cannot be established cheaply enough to trust the key. A symlinked file is followed and its target's bytes are hashed. |
| 17 | A watched tree records directories as digest-free entries, and leaves out `.git`, the target directory and every cache store root. A watch that resolves exactly at the target or a store root stores no whole-build entry. | A build script can list a directory, and an empty directory has no file digest, so a tree of files alone let `mkdir watched/empty` hit a stale entry. Recording the target or a store would instead invalidate on every build, which is why those are left out and the one watch that points straight at them refuses the entry. |
| 18 | Every `Cargo.toml` and `Cargo.lock` under the workspace root is keyed regardless of ignore rules, through a second walk with the ignore rules off that skips `.git`, the target directory and the cache store roots. | A `members = ["vendor/*"]` glob reaches a gitignored member, and no dep-info file mentions a manifest, so the per-file walk never saw it and editing the member's `[lib] path` hit a stale entry. The second walk collects only those two file names; an unreadable manifest is skipped so a cache problem cannot fail a build. |
| 19 | The stat cache distrusts a file whose mtime is within 2 s of now (racy clean), and a build that starts without `Cargo.lock` stores no whole-build entry. | A rewrite inside one clock tick keeps size, mtime and inode, so a cached digest can be stale the moment it is written; the same rule as the per-unit digest memo. An entry recorded before cargo wrote the lock names a key the next build can never compute, so it would never hit. |
| 20 | A registry unit runs no dep-info pre-pass: `# env-dep:` lines are read from the `.d` the real compile writes, stored in the entry with the values it saw, and compared against the current environment on every lookup, where any difference is a miss that the recompile then overwrites. The unit entry domain is `blitz-unit-v2`, so entries written before this miss. | The pre-pass cost every registry unit a second compiler process: on the engine release build 287 units ran it, about 2.4 s (4%) on a 55 s cold build, which was most of the per-unit overhead the reviewer measured. ccache's direct mode gets the same guarantee from the `.d` the compile writes anyway, and a recorded variable cannot produce a stale hit: an entry only answers a lookup when every variable it recorded still holds the value it recorded. |
| 21 | Known limit: a source rewrite that keeps size and mtime (only possible with a forged timestamp on a nanosecond filesystem) makes blitz miss, but cargo's own fingerprint still calls the old artifacts fresh, so the old binary is recorded under the new key. | Cargo has the same blind spot locally; changing how artifacts are recorded would stop caching every build whose units cargo already considers fresh. Recorded rather than fixed. |
| 22 | Known limit: an environment variable read by a proc macro at expansion time (`std::env::var` inside the macro) is not recorded by rustc's dep-info, so blitz cannot key it. | Cargo's own fingerprint has the same blindness. With a shared cache it means a fresh checkout can get output built under a different value. Proc macros should use `proc_macro::tracked_env` or a build script with `rerun-if-env-changed`. |
| 23 | Review round 3 fixes: a watched tree leaves out the target and cache-store directories themselves (not only their contents), and env-dep values keep trailing whitespace. Skip lists are spelled canonically once (`skip_path`) and shared by the walk, the lookup and the record. | The first made every project whose build script watches its package root miss after `rm -rf target` and on every fresh checkout; the second let `a` and `a  ` compare equal. Both reproduced, fixed, and re-run. |
| 24 | Known cost: keying every `Cargo.toml` regardless of ignore rules walks ignored trees by name; a 30,000-file ignored tree adds about 16-20 ms to a hit. | Correctness over speed: a manifest in an ignored member can change the build. flowmaster/engine's hit stays at 13 ms. |
| 25 | Incremental units are seeded and snapshotted around the compiler instead of passing straight through. The lineage key is the compiler identity, the chained driver, the crate name, crate types, `--test`, `--target`, the profile name, the normalized manifest, and the package name, version and manifest path inside the workspace, never the sources, the `--extern` digests or `-C metadata`. | rustc discards a session from a different command line, so the key has to describe the command, not the commit: a key that changed with every edit would never seed the case this exists for, and rustc checks what it reuses itself. The snapshot stores the newest finalized session plus its lock, because rustc will not load a session whose lock file is missing. What that is worth across checkouts is measured in decision 27. |
| 26 | A build script (`build_script_*`, crate type `bin`) is cached like a proc-macro: its key covers the linker and the SDK variables, its `<target>/<profile>/build/<pkg>-<hash>` out-dir maps to the target root so the `-L dependency=<target>/<profile>/deps` path normalizes, and its executable is restored with mode 0755. | A build script is a linked executable whose bytes depend on its sources and the linker, not on the workspace's code, and about a hundred of them ran uncached on every fresh CI build. Every other `bin` unit still passes through, because those link the workspace's own code. |
| 27 | Trust note and measured cost. An incremental snapshot is rustc object files and query caches handed back to rustc's own loader, so a poisoned entry could feed it forged intermediate state: the cache must be writable only by trusted builds, the same rule as the per-unit cache, and a read-only tier stays safe to share. The cross-checkout medians overlap (before [33.818, 24.787, 28.523] s, after [25.244, 24.604, 24.364] s), so they prove nothing either way and are not the evidence. The evidence is the same path: on fm-hel-03-ai, engine `cargo test --no-run`, CI paths, 4 jobs and an empty target after a one-line edit, seeding off took 79.4 s, seeding on 27.3 s, and 24.5 s with line-tables-only debug info (plain cargo cold 136.8 s, blitz cold 139.6 s, line-tables-only cold 120.6 s). On flowmaster/engine (debug, cold target) the two engine lineages snapshotted 261 files / 314.2 MB in 249 ms and 218 files / 54.1 MB in 100 ms, about 0.8% of a 44 s cold build. Cross-checkout reuse is small in practice: rustc discards a session whose command line differs, and a different checkout spells every path differently, so seeding pays when the same tree rebuilds after `cargo clean` or a deleted target, and inside CI from its second build on. | The trust boundary is the point of the row, and the numbers keep the benefit claim honest: the same-path gain is about 2.9x, while the cross-checkout medians are too close to separate from a loaded machine's noise. |
| 28 | A registry crate's build script is run through a `/bin/sh` shim left in place of its executable (`<file>.blitz-real` holds the real binary), and `blitz build-script-run` answers the run from the cache. Path and workspace crates keep the plain executable. | Cargo runs build scripts itself, so a per-unit hit still paid for the run every time, and on engine's CI build the `aws-lc-sys` run was 11.9 s of a 24.5 s edit build and the head of the critical path. Cargo hard-links the executable to `build-script-build` right after the wrapper returns, so whatever the wrapper leaves in that path is what runs. A shim that falls back to the real binary when the blitz it names is gone keeps a CI run whose blitz download failed working on the same target volume. Registry extractions are the crates whose sources cannot change under the key; a path crate's build script is recompiled whenever its sources change and its run is not the expensive one, so it stays untouched. |
| 29 | The run key (domain `blitz-bsrun-v1`) is the digest of the real executable, `OUT_DIR` as a literal path, the environment cargo sets for build scripts, the C tooling variables, the crate's own prefixed variables and the identity of `cc`, `c++`, `cmake`, `ar`, `ld` and `perl` on `PATH`. `CARGO_MAKEFLAGS` and `NUM_JOBS` are left out. | The script's own bytes cover a recompile, a new compiler or a new linker; nothing else in the environment notices those. `OUT_DIR` is printed into what cargo parses, so a different path is a different run, and CI spells it identically every time. `CARGO_MAKEFLAGS` carries a jobserver token that changes on every build, and `NUM_JOBS` describes the machine, not the output: including either would turn every hit into a miss. The C tooling variables and the tool identities are what actually decide a build script's bytes when it drives a compiler. |
| 30 | Runs use a direct mode: the stdout of a stored run is parsed for `cargo:rerun-if-env-changed` and `cargo:rerun-if-changed`, and every recorded value is compared on lookup. A `rerun-if-changed` path outside the crate and outside `OUT_DIR` is stored with a file digest; a path that resolves to a directory or a special file makes the run uncacheable. Paths inside the crate are left out. | A table-driven build script (`aws-lc-sys`) switches on `AWS_LC_SYS_*` and prints those names itself, so the only honest way to cache it is to believe what it says and verify it. A directory has no digest blitz can trust cheaply, and guessing would be a stale hit; inside the crate, the script's own bytes already change with its sources. |
| 31 | A run is restored only into an empty or missing `OUT_DIR`, keeps file modes and symlinks, refuses absolute or `..` names, replays stdout byte for byte and never changes the script's exit code; any error runs the real binary. A restore that fails halfway removes `OUT_DIR` again. | Cargo parses the stdout, so it is the one stream that must be exact, and anything already in `OUT_DIR` belongs to this run. A cache may cost a run, never a build: every failure path ends in the real script, and a half-restored `OUT_DIR` would make that script fail where it would have succeeded. |
| 32 | Session attribution after review round 1: the crate directories and their newest sessions are recorded before the compile, and the snapshot stores the newest session that changed during it; two changed sessions with the same timestamp are ambiguous and nothing is stored. | The first version skipped whenever more than one directory changed, and a crate whose library and test build compile together (engine) then never snapshotted: the CI edit run went from 24.5 s to 41.5 s. The compiler that just exited wrote the newest session, so the newest changed one is this invocation's; the guard only covers sessions that cannot be ordered, which a real filesystem timestamp makes vanishingly rare. |
| 33 | The run cache is worth 1.7x against a same-day v0.2 control (23.8 s to 14.0 s) and 2.4x against the same binary with the run cache switched off (29.3 s to 12.4 s); the run of `aws-lc-sys` falls from 11.45 s to 0.12 s, and engine starts at 2.39 s instead of 12.57 s. Numbers and method in `docs/benchmarks.md`. | The claim has to be the measured one, including the control measured the same day, because the earlier 24.5 s figure came from a shared host hours apart. |
